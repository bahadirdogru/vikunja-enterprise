Getting started

On this page
  • Quick start with Docker
  • Docker Compose
  • Choosing a database
  • Behind a reverse proxy

  • Where to go next

vikunja-enterprise is one container image: the API, the web app and the background workers run in one process on port 3456. You need Docker (or any OCI runtime), a place to keep two directories, and, if you do not want SQLite, a database server.

Important

This is a development fork. Read the roadmap and status before you rely on it for anything that matters, and take a backup before every upgrade. It is not an official Vikunja product; see the relationship to upstream.

Quick start with Docker #

The image is built from the repository's Dockerfile as one binary on a scratch base. The API and the web frontend are served by the same process on port 3456, and the container runs as user 1000.

mkdir -p vikunja/db vikunja/files
sudo chown -R 1000:1000 vikunja

docker run -d --name vikunja \
  -p 3456:3456 \
  -e VIKUNJA_SERVICE_PUBLICURL=https://tasks.example.com/ \
  -e VIKUNJA_SERVICE_SECRET=change-me-to-a-long-random-string \
  -v "$PWD/vikunja/db:/db" \
  -v "$PWD/vikunja/files:/app/vikunja/files" \
  ghcr.io/bahadirdogru/vikunja-enterprise:main

CI publishes the image with .github/workflows/enterprise-docker.yml: the tags main and sha-<short> on pushes to main, and <tag> plus latest for tags that start with e.

  • Database. Without further settings the image uses SQLite at /db/vikunja.db (VIKUNJA_DATABASE_PATH), so mount /db and make it writable for user 1000. For MySQL or PostgreSQL set VIKUNJA_DATABASE_TYPE and the connection settings. The fork is tested on PostgreSQL 18 and 19 and on MySQL 8; for PostgreSQL, 18 or newer is recommended. Upstream's documented minimum versions still apply to the code but are not tested here.
  • Files. Attachments go to files (files.basepath) relative to the root path, which the image sets to /app/vikunja/.
  • Secret. Set service.secret. It signs tokens, and if it is unset a random one is generated at every start, which invalidates all issued tokens on each restart. Project secrets of automation rules are encrypted with it as well, so changing it makes them unreadable until they are set again.
  • Public URL. Set service.publicurl to the address people really use. Incoming webhook addresses and e-mail links are built from it. Public forms are served from /forms/<token> on the same origin.
  • Reverse proxy. Put TLS in front, and check service.ipextractionmethod and service.trustedproxies: the per-IP limits of public forms and webhooks use the address the router determines.
  • arm64. The arm64 image is built in CI but has not been started on real ARM hardware yet.

Settings come from config.yml or VIKUNJA_* environment variables. The fork's own keys, their defaults and their meaning are listed per module in docs/modules/; the full list is config-raw.json. For everything generic (mail, authentication, reverse proxy examples, upgrades, backups) the upstream installation docs apply.

Docker Compose #

The same setup as a Compose file, with PostgreSQL. It is an example assembled from the settings above, not a file the project ships or tests: change the host name, the passwords and the secret, and check the image tag.

services:
  vikunja:
    image: ghcr.io/bahadirdogru/vikunja-enterprise:main
    ports:
      - "3456:3456"
    environment:
      VIKUNJA_SERVICE_PUBLICURL: https://tasks.example.com/
      VIKUNJA_SERVICE_SECRET: change-me-to-a-long-random-string
      VIKUNJA_DATABASE_TYPE: postgres
      VIKUNJA_DATABASE_HOST: db
      VIKUNJA_DATABASE_USER: vikunja
      VIKUNJA_DATABASE_PASSWORD: change-me
      VIKUNJA_DATABASE_DATABASE: vikunja
    volumes:
      - ./files:/app/vikunja/files
    depends_on:
      - db
    restart: unless-stopped
  db:
    image: postgres:18
    environment:
      POSTGRES_USER: vikunja
      POSTGRES_PASSWORD: change-me
      POSTGRES_DB: vikunja
    volumes:
      - ./db:/var/lib/postgresql
    restart: unless-stopped

The files directory must be writable for user 1000, as in the docker run example. Create it first and change its owner.

Choosing a database #

DatabaseStatus in this fork
SQLiteThe default and the simplest choice for a small group. The backend test suites pass on it.
PostgreSQLTested on 18 and 19; 18 or newer is recommended.
MySQLTested on 8.
MariaDBSupported by upstream; not tested in this fork.
Older versionsUpstream documents lower minimum versions. The code is written for them, but they are not tested here.

Which suites were run on which database, and when, is recorded in the roadmap; that page is the source of truth, not this table. Raw SQL and migrations in the fork follow upstream's supported databases.

Pick the database once. Moving an existing instance between engines is not something the fork provides or has tested.

Behind a reverse proxy #

Put TLS in front of the container with any reverse proxy and forward everything to port 3456. Three settings matter:

  • service.publicurl must be the address people really use, with the scheme. Links in e-mails and the addresses of incoming webhooks are built from it.
  • service.ipextractionmethod and service.trustedproxies decide which client address the server sees. Public forms and incoming webhooks have per-IP rate limits, so a wrong value either blocks everybody behind one address or lets a caller choose their own.
  • Forward the Host header and, for xff, X-Forwarded-For.

A minimal nginx location, as an example for you to adapt:

location / {
    proxy_pass http://127.0.0.1:3456;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-For $remote_addr;
    proxy_set_header X-Forwarded-Proto $scheme;
    client_max_body_size 20m;
}

Run the container with VIKUNJA_SERVICE_IPEXTRACTIONMETHOD=xff and VIKUNJA_SERVICE_TRUSTEDPROXIES set to the address range of your proxy. Upstream has more reverse proxy examples in its installation documentation (upstream's page, not this fork's).

Upgrading #

  1. Take a backup (below).
  2. Pull the image tag you run. The tag main moves with every push to main; to stay on a known build, use the sha-<short> tag of a commit instead.
  3. Recreate the container. The database schema is migrated when the process starts, as in upstream, so the first start after an upgrade can take longer.
  4. Check the log and open the app.

There is no downgrade path. If an upgrade goes wrong, restore the backup and start the old image. The fork merges upstream's main from time to time with no promised schedule; see the roadmap for what has been verified.

Backups #

Back up three things together, and keep the secret with them:

  • The database. For SQLite, stop the container and copy the file (or use sqlite3 vikunja.db ".backup backup.db" on a running instance). For PostgreSQL use pg_dump, for MySQL mysqldump.
  • The files directory (/app/vikunja/files), which holds attachments.
  • Your settings, in particular service.secret. It signs login tokens, and the encrypted project secrets of automation rules are encrypted with a key derived from it. A restored database with a different secret cannot read them.

Test the restore at least once on a spare machine.
