vikunja-enterprise roadmap

On this page
  • Principles
  • Status
  • Log
  • Remaining

vikunja-enterprise is an independent, community fork of Vikunja (AGPL-3.0-or-later). It is not an official Vikunja product.

Principles #

  • One image, one process. A single Docker image (amd64 + arm64). No Redis requirement, no separate worker containers. Durable background work uses a database outbox.
  • Small upstream diff. New features live in their own files/packages and tables; upstream files are touched as little as possible so upstream can be merged regularly.
  • Everything unlocked. No license key, no feature gating.
  • New API routes go on /api/v2.
  • Databases. The fork is tested and supported on SQLite and PostgreSQL. MySQL and MariaDB are compatible by design (portable SQL, upstream's rules) but are not tested and not guaranteed. Decided on 2026-11-25; entries in the log before that date also report MySQL 8 runs, the last on that day.
  • Organisation / multi-tenant hierarchy is deferred until there is a real need.

  • Automation scripts run in child processes. goja checks its interrupt only between instructions, so one native call ran past the timeout. Of 70 surveyed calls (array built-ins on {length: 2**53 - 1}, also through Reflect.apply, bound functions, a Proxy and iterators; typed arrays; repeat / padStart; JSON.stringify; eval and new Function of huge sources; BigInt) at a 200 ms timeout, 27 still ran after 10 s, 23 hit a fatal out-of-memory error (under a 3 GiB cap; in the server that error ends the process) and 8 overran by 0.5 to 7 s. Now every script, and the compile check on save, runs in the same binary re-executed with an empty environment; host calls come back over a pipe and are answered in the step's transaction. The process is killed 0.5 s after the timeout, has an address-space limit (automation.scripts.maxmemory, 256 MiB) and a CPU limit on Linux, and dies with the server; one that finished in time is pooled (workers + 1). All 70 now end within timeout + 0.5 s: as a timeout, a memory error or the built-in's own exception (4 find* calls on an array-like hit a nil-pointer panic in goja, reported as an internal error, before and after). Overhead 0.8 ms per script pooled, 25 ms per process start (0.2 ms in-process before). Wrapping the built-ins was rejected: the class is open-ended. Not closed: the memory limit is only soft on macOS and Windows; a script still costs up to one core for its timeout + 0.5 s; idle pooled processes take about 13 MB each.

  • Script processes, adversarial review. A pooled process kept the previous script's heap: two new Float64Array(20*2**20) in one process, the second failed with the memory error and counted against its (maybe another project's) rule. Now the heap is collected and returned between scripts when more than 8 MiB of garbage is left, MALLOC_ARENA_MAX=1 stops glibc from reserving 64 MiB of address space per thread, and the child reports its spare address space: a process is pooled only after a success or an ordinary exception and within 32 MiB of a new one, else retired. The CPU rlimit did nothing (Go ignores SIGXCPU); a watchdog goroutine in the child exits 1.5 s after the deadline or when stdin closes or the parent changes; preemption lets it run inside a native call with GOMAXPROCS=1 (a child whose parent was SIGKILLed while it spun in indexOf: gone after 0.04 s, before still running at 30 s). Children are /proc/self/exe on Linux and must send a hello with protocol and build within 5 s; started from one locked thread (Pdeathsig). Live processes capped at workers + 2 (dry runs and checks share 2, wait within their timeout, else "busy"). Lines over 4 MiB are refused before buffering (was 32 MiB with two copies); results, errors and logs are cut in the child; the parent counts calls and requests and checks sizes again; sequence numbers; unread output kills; the child gets oom_score_adj 1000. Machinery failures (spawn, hello, protocol, busy, unexplained death) are temporary and, when the retries run out, do not count towards disabling the rule; a SIGKILL not sent by the server counts as the script's memory. NaN, Infinity and -0 from the host reach the script unchanged. The compile check takes the request context. Headroom at 256 MiB: 190 MiB in one typed array, 390000 small objects, 2.1 million short strings (default kept). Overhead 0.7 ms per pooled script (0.3 ms before with this development build), 28 ms per process start; idle pooled process 65 MB private with a development build. Not closed: host calls do not take the deadline (a worker is held for timeout + 0.5 s + the host call in flight); the memory limit is soft on macOS, the BSDs and Windows (no Job Objects); the child is no sandbox (same uid, reused across projects).

  • Script processes, second review. The server built the whole JSON of the start and of every host-call answer (HTML escaped, 6 bytes per <) before the child refused it at 64 MiB: tasks.find of 100 tasks with 1 MiB descriptions took 2.3 GiB in one call, 4 runs on a 20 MiB task 1.4 GiB, and the child's death was "unavailable", retried five times and never counted. Now both directions are estimated before encoding (8 MiB to the child, no HTML escapes): an answer above it is an exception in the script, a task above it fails the step for good without blame (anyone with write access can make one; fields are not cut, a script writing one back would destroy it). Measured after: 0 MiB extra for both repros. Blame is default-deny once the start was sent (an exit code, closed output or garbage from the child is the script's), except a SIGKILL the server did not send: not counted, retried only before an http.fetch (else failed, since a retry repeats the request). The hello has its own 5 s; the compile check never falls back to compiling in the server (it refused the save instead; 7.9 s in the server reproduced before). One interactive process per project. Lost wake-up of waiters fixed, memory message says "hit the memory limit of N MiB", one error at worker start when scripts cannot run, every run of a given-up event fails with its own rule's error, the child is started with an argument so an upstream binary stops with "unknown command". Not closed: two projects can still hold both extra processes; memory pressure on the server can fail any rule's run (not counted); the child is no sandbox.

  • Script processes, third pass: an answer too large for the script that it does not catch is not counted either (someone with write access to a task the owner can read could otherwise get the rule disabled); payloads nested deeper than 1000 levels are refused like oversized ones and keep the process; specials count in the size estimate; a save checks only new or changed script sources, so a rule can be disabled while checking is unavailable.

  • Review-pass operational notes: run code generators with LC_ALL=C on machines with a Turkish locale (the dotless i breaks generated identifiers). Vitest's on-disk module cache is disabled in frontend/vite.config.ts (fsModuleCache: false) because cached transforms broke the i18n virtual modules on repeat runs.

  • Automation: cap on rules per project. automation.maxrulesperproject (default 100; 0 or less is replaced with the default like automation.maxpendingwaits). Creating a rule and duplicating a project (copies are refused whole, never half) over the cap answer 409 with code 22014 (en and tr message, shown at the top of the rule editor). A project already above the cap keeps its rules: they run and can be edited, disabled and deleted. The count and the insert are not locked together (no engine-specific SQL), so concurrent creates can overshoot by about the number of requests in flight. Checked with model and /api/v2 tests; not checked in a browser.

  • Automation: replay protection for the incoming webhook. A call to a hook that names a secret now carries X-Vikunja-Timestamp and X-Vikunja-Signature: sha256= + HMAC-SHA256 over timestamp.token.body (the token of the hook URL, so a call signed for one hook is refused by a sibling hook with the same secret) (unreleased trigger, so the body-only signature is refused, not kept). Timestamp window automation.webhook.tolerance (default 5m, 0 or less becomes the default), up to 1 minute ahead accepted. Accepted signatures are kept in the new table automation_webhook_seen (unique on rule and signature, migration 20261128100000) because several instances can share one database and the keyvalue store is per process unless Redis is configured; the row is inserted in the transaction of the queued event, so a call refused for its payload or the rate limit does not use its signature up, and two identical calls at once race on the unique index (6 parallel identical calls: exactly 1 accepted, run on SQLite). The row keeps the signed timestamp (signed_at); the 30 s ticker deletes rows older than this instance's tolerance plus 2 minutes, which assumes instance clocks within that margin and one tolerance for all instances. A replay is looked up before the rate limit, so it is a 401 and costs no budget. Bad signature, malformed or missing header, stale or future timestamp and replay are one 401 / 22011 answer (reason only in the debug log). Hooks WITHOUT a secret stay callable unsigned and are not replay protected; this is documented. Verified: unit tests (valid, replay, stale, future, body-only signature, tampered body, malformed headers, unsigned hook unchanged, expiry cleanup, ticker cleanup, concurrent replay), /api/v2 tests, the migration test (unique index, expiry index), the editor strings (en and tr) in vitest. Not checked: two real server processes against one PostgreSQL or MySQL (the cross-instance refusal is shown by the memory being a table, in one process), the editor text in a browser, a sender in another language. A retry of an accepted call was refused like a replay at that time (changed later: it now gets the 202 of the first call, see the entry on the retry of an accepted call). automation.webhook.tolerance needs a unit and at least 1s (a bare 300 is nanoseconds and would refuse every call: it falls back to the default with a warning). Changing automation.webhook.tolerance upward does not bring back rows already deleted: calls captured earlier can be replayed until their new window ends.

  • Hardening verification (cap on rules per project and replay protection): mage test:feature and mage test:web pass uncached (GOFLAGS=-count=1) on SQLite, PostgreSQL 18 and MySQL 8, one database at a time. MySQL found the first draft of the new table: xorm builds the unique index name from the table name and the index name, and 64 characters is the limit there; the index is now called rule_sig. mage lint reports only the 12 known unused findings in pkg/license/. A review of these changes then found and fixed: replay across sibling hooks with one secret, a stale curl example in API.md (both examples' signature now checked against the Go helper with openssl), clock-skew dependent row expiry, files of a refused project duplicate (now refused before anything is written), and a replay that was answered 429 instead of 401. Re-verified on SQLite, PostgreSQL 18 and MySQL 8, see the report of that pass.

  • Approvals and disabled accounts (fixed). Disabling an account (ChangeUserStatus, the one function behind the admin routes and the CLI) now drops it from the undecided slots of every pending request in the same transaction, with the code path of a deleted user: a request that waited only for it ends as no_approvers, one where everybody who is left approved is approved. An approved transition for a requester whose account is disabled is not performed: the request ends cancelled with the new reason requester_disabled (decisions stay, no history row, the usual resolved event and notification). A disabled approver could already not decide and was already not asked. Verified: the new tests in approvals_disabled_test.go failed before the change and pass after it; TestApprovals*, TestAdmin* and TestUser* pass on SQLite; the frontend cancel-reason test passes.

  • Workflow, removing a status with move_tasks_to (fixed). Each moved task now gets a status history row (comment Moved because the status "<title>" was removed from the workflow., doer is the person who saved the workflow) and a task.status.changed event, plus task.updated when the category change flips the done flag. Chunks of 200 tasks in the transaction of the removal: 4 statements per chunk, 4 * ceil(N/200) for N tasks, N to 2N events held until the commit. Verified: the new tests in workflow_status_move_test.go failed before the change and pass after it; TestWorkflow* and TestApprovals* pass on SQLite. Not measured with a large N.

  • Custom field limits (fixed). New keys customfields.maxfieldsperproject (100) and customfields.maxoptionsperfield (200), error codes 20006 (409), 20007 (400) and 20008 (400, also an invalid value to code that checks for one, so forms need no change). Only adding is refused: a project or field that is already above the limit keeps working, can be edited, and an option list can shrink. Text, long text, url and email values are checked in bytes against 65535, the size of MySQL's text column, so a value that one database stores all three store; multi-byte characters count with their bytes. The messages of the three codes are in the error table of both frontend languages (with the limit as parameter) and the value editor checks the byte length before sending. Verified: the new Go tests failed before the change and pass after it (custom_field_limits_test.go, the wire test huma_custom_field_limits_test.go), the vitest tests of the helper and the message table pass; en and tr keys and placeholders are identical. Remaining #

  • Workflow: a save that would move or change more than 20000 tasks is refused (21011) and there is no tool to get below the limit: no bulk status change exists, the limit is not a config key, and changing the category of a large status, a cheap bulk update before, is refused as well. The way out today is one status change per task through the API.
  • Workflow: on PostgreSQL a task can be left on a removed (archived) status when another request moves it into that status in the instant the save removes it; the save locks the tasks it finds, not the status. Older than the review rounds, not fixed.
  • Approvals and workflow: three paths take several task locks out of task id order (a category flip before the removal lock in one save, the two passes of a user deletion, tasks that arrive in a removed status after the first lock). A deadlock needs a second multi-task locker on the same tasks at the same time; the database then aborts one of them with an error.
  • Upstream test TestConnectionAuth/closes_the_socket_when_the_token_expires (pkg/websocket, untouched by the fork) failed once on PostgreSQL in a full run and passed six times in a row afterwards; cause not established.
  • Workflow: changing the category of a status in the editor flips the done flag of its tasks (and announces task.updated), but does not move them to the done bucket of manual kanban views; tasks moved because their status was removed do.
  • Default dashboards for new projects with a workflow (4c).
  • MCP exposure of the fork's endpoints; the new automation routes are not in the MCP allow-list.
  • The arm64 image has not been started on real ARM hardware. MySQL, MariaDB and the documented minimum database versions are not tested.
  • The parts of the newest UI listed as not run end to end in the browser pass above (ticker-driven rules, wait, HMAC, workload estimate field, Turkish strings).
  • Automation: the catalog does not expose automation.waitmax or service.timezone to the editor; the stuck-run reaper does not disable rules or update metrics; the stop step is still recognised by an output prefix; no templates gallery for the 3d types; no e-mail action.

Open after the review pass, not fixed because they need a decision:

  • Automation: goja's find, findIndex, findLast and findLastIndex on an array-like hit a nil-pointer panic (reported as an internal error).
  • SQLite: a transaction that reads and then writes fails at once when another connection holds the write lock (_txlock=immediate would change that for every transaction).
