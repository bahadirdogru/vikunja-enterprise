vikunja-enterprise keeps upstream's Go API and Vue 3 frontend and adds custom fields, workflows and approvals, automation, dashboards and forms on top.

Why this fork

The aim is a copy of Vikunja that is complete and properly built in every respect up to enterprise level, true to the spirit of the original, and accessible to everyone. It is an aim, not a finished state: the status section says what is done and what is not.

"True to the spirit of Vikunja" is meant in concrete terms, and only as far as the repository supports it:

  • Same stackGo API and Vue 3 frontend, as upstream.
  • One binaryThe API and the web UI are served by the same process on port 3456. Automation runs inside it too, with no separate worker container.
  • Self-hostedOne image, linux/amd64 and linux/arm64. SQLite by default; MySQL and PostgreSQL are supported.
  • AGPL-3.0-or-laterSame license as upstream.
  • Small diff to upstreamNew features live in their own packages and tables so upstream can be merged. There is no promised sync schedule.
  • No license keyUpstream gates a few optional features behind a key. Here nothing reads a key or contacts a license server, so those features are simply on.

What it adds

Five modules on top of upstream. All new API routes are on /api/v2. The diagrams are schematic illustrations of the ideas, not screenshots.

01

Custom fields

  • Thirteen per-project field types, from text and number to select, user, rating and progress, validated per type.
  • Filter and sort tasks by field in the API; in the filter input you type the field name, so renaming a field does not break a saved filter.
  • Show values in task lists, table columns and on kanban cards.
  • Fields can be required on workflow transitions, used in automation and asked for in forms.
Design document on GitHub
02

Workflows and approvals

  • Real statuses per project, each with a category (including done and cancelled), independent of kanban buckets, with a status history per task.
  • Optional restriction to listed transitions, with per-transition rules: minimum permission, allowed teams, required fields and a required comment.
  • A transition can require approval from one or several approvers, in mode "any" or "all", with a deadline.
  • Kanban status mode: columns are statuses and a drag is a transition. Filter and sort by status.
Workflow design · Approvals design
03

Automation

  • Rules of the form When / If / Then, run from a database outbox by workers inside the same process.
  • Triggers include task events, status and field changes, schedules (cron), overdue and due soon, a manual run, and incoming webhooks with a secret URL and optional HMAC signature.
  • Actions include setting fields, changing status, assigning, commenting, creating tasks, notifying, requesting approval, waiting, signed http.request calls and sandboxed JavaScript.
  • Dry run, a recorded history of every run with retry, and configurable limits and kill switches.
Design document on GitHub
04

Dashboards and reports

  • Dashboards of widgets over task filters; every number is computed over the tasks the viewer can read.
  • Widgets: number (with previous-period comparison), bar, donut, line, created vs done, task list, text, time in status, workload and time tracking.
  • A drag-and-resize grid, a widget editor with live preview, and drill-down to the tasks behind a value.
  • An aggregation API (POST /api/v2/reports/tasks) and CSV export.
Design document on GitHub
05

Forms

  • A builder in project settings with a live preview; fields map to task fields, labels, attachments and custom fields, and hidden fields can pre-set a value.
  • Access for project members, any signed-in user, or public through a standalone page without login.
  • Submissions create the task through the normal create path, so workflows, validation and automation apply; form.submitted is an automation trigger.
  • Public forms are protected by rate limits, a honeypot, size limits, an optional submission cap and a close date. Public attachments are off by default.
Design document on GitHub

How it fits together

One process serves the API and the web UI. Automation events are written to a database outbox and picked up by workers in the same process; a ticker handles schedules and due dates.

  • OutboxA transactional outbox in the database makes background work durable. No Redis requirement.
  • Same permissionsReports and dashboards only count tasks the viewer can read; form submissions create the task as the form owner through the normal create path.
  • Same originPublic forms are served from /forms/<token> on the same address as the app.

Quick start

The image is built from the repository's Dockerfile as one binary on a scratch base. Replace the public URL and the secret before you run it.

bash
mkdir -p vikunja/db vikunja/files
sudo chown -R 1000:1000 vikunja

docker run -d --name vikunja \
  -p 3456:3456 \
  -e VIKUNJA_SERVICE_PUBLICURL=https://tasks.example.com/ \
  -e VIKUNJA_SERVICE_SECRET=change-me-to-a-long-random-string \
  -v "$PWD/vikunja/db:/db" \
  -v "$PWD/vikunja/files:/app/vikunja/files" \
  ghcr.io/bahadirdogru/vikunja-enterprise:main

  • Port 3456. The API and the web frontend share it. The container runs as user 1000, so the mounted directories must be writable for that user.
  • service.publicurl. Set it to the address people really use. Incoming webhook addresses and links in e-mails are built from it.
  • service.secret. It signs tokens. If unset, a random one is generated at every start, which invalidates all issued tokens on each restart. Encrypted project secrets of automation rules depend on it too.
  • Volumes. Without further settings the image uses SQLite at /db/vikunja.db, so mount /db. Attachments go to /app/vikunja/files.
  • Behind a proxy. Put TLS in front and check service.ipextractionmethod and service.trustedproxies.

Every setting is listed in config-raw.json; the README covers the fork-specific keys, and the upstream installation docs cover everything generic.

Status and roadmap

This is a development fork. Read this before relying on it. The roadmap is the source of truth for what is done, what has been tested, and the test results per database.

Implemented

  • Custom fields, workflows, approvals, automation, dashboards and reports, and forms, each with backend and web UI.
  • No license key needed; multi-arch image published from CI.

Tested

  • Backend test suites have been run on SQLite and PostgreSQL; MySQL only partly. See the roadmap for the details and the date of the last pass.
  • Documented database minimums come from the SQL in the code and are not tested in CI.

Not yet verified

  • The newest UI parts (form branding, new dashboard widgets and CSV export, automation time triggers and manual run) are not checked in a browser.
  • The arm64 image has not been started on real ARM hardware.
  • Several design decisions are open and listed in the roadmap.

Known gaps

  • The incoming webhook signature covers the body only, with no replay protection.
  • The fork's endpoints are not exposed over MCP.
  • Default dashboards for new workflow projects are not created yet.
  • Scripts have no hard memory cap; scripts can be switched off with automation.scripts.enabled.

Deferred

  • Organisation and multi-tenant hierarchy.
  • AI features.

Relationship to upstream

The fork was created from upstream main (v2.8.0-187) and aims to keep its diff to upstream small so that upstream can be merged. /api/v1 is frozen and only gets bug fixes and ports; everything the fork adds is on /api/v2. Upstream's documentation applies to everything this site does not list.

Almost everything here is the Vikunja project's work. It is not affiliated with, endorsed by or supported by this fork. Please do not send fork problems to the upstream maintainers. For security issues in the fork's own code, see the README.
